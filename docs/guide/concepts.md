# 平台概念

## 平台、比赛与队伍

一个 NoCTF 部署可以举办多场比赛。每场比赛只选择一种模式，拥有自己的报名规则、队伍、题目实例、计分和排行榜。一个账号在同一比赛中只能属于一个队伍，但可以在不同比赛参加不同队伍。

队伍由成员和队长组成。队长必须是本队成员，负责提交报名、维护组织资料和管理成员。创建队伍只是报名草稿，只有 Approved 且未被封禁的队伍才具有正式参赛权限。

## LiveSolo 的 Match 与 Round

LiveSolo 是第五赛制，一场比赛可有多场两队 Match，每场通过多个 Round 累计胜局。名单按 Match 锁定，题目、附件、Runtime、Flag 与受理顺序按 RoundQuestion 作用域隔离。

它不使用普通题目积分/血奖，胜局由共同受理序号中第一条有效正确 Flag 决定。媒体就绪、延迟节目、录像及纠正属于独立操作，见 [专用手册](../live-solo/index.md)。前四赛制保持各自原有规则。

## 题库模板与比赛题目

| 概念 | 管理内容 | 影响范围 |
| --- | --- | --- |
| 题库模板 `Challenge` | 题面、方向、附件、Flag、Runtime、Checker、注入定义 | 所有引用此模板的比赛 |
| 比赛题目 `CompetitionChallenge` | 展示名称、排序、发布、计分规则、提示 | 当前比赛 |

先在题库创建模板，再在比赛中引用。模板的模式必须与比赛一致。比赛中修改展示名称不会修改题库标题；修改模板题面会被引用方读取，修改 Runtime 定义则在后续启动或重置时使用，已有运行环境不会自动替换。

## Runtime、Checker 与 Flag

**Runtime** 是题目的执行环境。静态题可以没有 Runtime；CTF 通常由选手按队启动，AWD 由平台管理每队目标，KoH 是全体队伍攻击同一共享 Hill。

**Checker** 执行服务健康检查、修复包验证等任务。环境可以访问不代表 Checker 已经成功，Checker 的镜像、回调和协议需要单独验证。

**Flag** 是平台用于验证答案或控制权的内容。模板静态 Flag、比赛专属 Flag、Runtime 动态 Flag 的作用域不同。AWDP 的 Break 是正确 Flag 提交，Fix 是独立修复包提交，不能混成同一种动作。

## 事实、评测与排行榜

一次 Flag、Fix、提示解锁或人工调分形成比赛行为事实 `GameplayFact`。评测更新该事实的当前结果；排行榜根据当前有效事实重新计算。重判、封禁、赛道变化都可能使历史记录的计分改变。

上段的普通积分投影用于前四赛制。LiveSolo 复用行为与评测基础，但结果进入独立胜局和赛程，普通人工积分调整不能代替 Match 纠正。

实时消息只是刷新提示。浏览器断线后，重新读取页面得到的状态比旧通知可靠。赛事“动态”、个人消息中心和题目页“赛事播报”展示范围不同。

## Host 与基础设施

`NoCTF.Host` 是唯一可执行程序，可同时启用 Api、Worker、Runner，或在多个进程中按角色拆分：

| 组件 | 职责 |
| --- | --- |
| Api | 页面/API、认证授权、文件访问、SignalR |
| Worker | 评测业务、生命周期、通知、排行榜、Webhook |
| Runner | 启停题目环境，执行 Checker 与修复验证 |
| PostgreSQL | 权威业务数据 |
| NATS JetStream | 持久消息、短租约与资源域协调 |
| Redis | 可重建缓存和实时通信 backplane |
| Local / S3 | 文件和修复包对象存储 |

单次部署在平台配置中选择一个容器 Runtime Provider：Docker 或 Kubernetes，并指定 Runner Pool。比赛和题目不自行选择 Provider。不要把题目的命名服务配置当作 Docker Compose 文件导入。
