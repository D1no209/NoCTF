# 提交评测、重判与证据

## 查询尝试

入口 `/admin/competitions/比赛ID/submissions`。当前表单按题目、队伍、动作、处理状态、结果和 Flag 相关过滤项查询，使用 cursor“加载更多”；换筛选重新开始，不能只检查屏幕第一批记录就声称没有其他尝试。

在比赛管理“提交/评测”查看题目、队伍、发生时间、动作类型、处理状态、当前结果和失败代码。页面名称可能使用“提交”，底层当前记录是 GameplayFact；一次重判更新该事实当前结果，不复制一套评分历史。

CTF Flag、AWDP Break、Fix、系统健康/控制观察和人工调分的含义不同。筛选具体动作后核对，不把系统观察当作选手提交。

## 异步状态与结果

受理后会有 Pending/处理中等状态，再得到最终结果。等待时检查 Worker、Runner、镜像和存储；管理员不能用手动调分掩盖整个判题队列故障。

| 情况 | 判读方式 |
| --- | --- |
| Correct | 当前正确事实按模式与资格计分 |
| Wrong / 修复失败 | 按该模式扣分和尝试政策处理 |
| Rejected | 格式、归档或业务约束拒绝 |
| PlatformFailed | 平台、存储或执行依赖故障，检查稳定 failure code |

最终状态名以页面/API 当前协议为准。内部错误细节与受保护 Flag 不向普通选手公开。

## 派发与重判

AWDP 可配置自动或手动评测。手动模式由有权限裁判选择待判记录派发，按运行资源预算控制批量规模。

重判前确认修正了什么：Flag 定义、Checker 逻辑、运行故障还是误判。选取精确队伍、题目和时间范围，评估是否影响血榜、动态分值和赛道竞争；执行后等待事实最终结果与排行榜刷新。

修改分值配置只会重算投影，不重新执行 Checker；重判会重新评估相关事实。这两种操作需要分别判断。

## 单条、题目批量与评测队列

单条重判作用于选中的 GameplayFact UUID。当前批量重判按所选 **CompetitionChallenge** 派发，不只重判屏幕上可见的筛选结果；检查题目影响范围后再执行。

手动评测队列同样按所选比赛题目触发，适用于当前调度政策允许的待判记录。受理后等待完成，避免重复派发造成不必要的 Runner 工作。

## 评测证据与历史差异预览

详情提供关联评测/裁定事件读取，分页查看证据链、时间、分类与完整性。差异预览比较当前权威判定与历史证据信息，可选择是否包含 informational 项，并展示扫描事实数量。

差异预览是读取操作，不会自动重判或调分。缺失证据、未扫描完、信息类差异与严重差异分开判断，再选择明确的重判目标。当前事实仍只有一个现行结果，事件展示不等于另一套评分账本。

## Flag 原文与 Fix 文件

尝试详情点击原文查看会执行专门受保护读取；当前原文弹窗不要求输入理由，服务器仍检查权限，比赛协作者成功读取有访问事件。不要编造隐藏字段或让选手代管理员提供 Token。

Fix 详情按权限下载实际 patch archive，核对 fact ID、文件 hash/长度和格式再调查。无权限、没有对应 patch 与存储故障不同，不把下载失败直接判为修复错误。

## 人工调分

在管理评分或题解审核入口输入非零有符号 Int32，例如 `-10` 扣分、`25` 补分。必须处于 `-2147483648` 到 `2147483647` 范围，0 不是有效调整。

人工调整创建独立事实，不覆盖原 Flag 或 Fix。执行前核对比赛、队伍、题目、当前权威分数与原因。题解审核的“扣除题目当前得分”会根据当前净得分创建相反 delta，将当前净额调至 0；后续规则或重判变化仍可能改变净额。

受理后等待权威榜同步，避免因为 UI 暂时超时重复调分。先查看是否已经产生调整事实，再决定是否需要新操作。

## 封禁申诉与纠正

封禁保留不可变事件；队长针对该事件提交一次私密申诉。Administrator、Owner、Manager 裁决，Judge/Observer 按读取权限查看。接受申诉或主动纠正会关联原始事件，不公开工作人员原因和证据。

解除后历史事实重新参与投影。CTF 环境由选手重新启动，AWD 可由系统重新配置；Finished 不再重新启动正式环境。

## 核对最终成绩

统一检查当前资格、赛道、模式规则、首次正确事实、错误/提示罚分、人工 delta 和榜单可见性。正式导出前等待投影就绪，记录导出时间与当前配置版本的 Git/部署背景，避免把冻结公开榜当成最新管理榜。
