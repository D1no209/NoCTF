# 能力配置与容器判定升级

新建模板填写标题、可见性、方向、题面和能力选择，容器及能力参数在详情中配置。详情侧栏按当前草稿显示对应配置页，基本信息、运行环境及能力参数通过一次完整 `content` PATCH 保存，允许先保存未完成的配置。关闭能力后，保存前重新启用可恢复参数；保存后仅保留已启用能力。静态 Flag、附件和权限分别管理。未保存的技术配置禁止测试和投放，仅修改标题、题面等基础信息不会阻止这些操作。离开页面提供未保存提示。

Check 的必需证据由消费场景产生：AWD 使用本次任务的连接、功能和 Flag 上下文，Fix→Check 要求功能与漏洞判定，独立模板测试接受非空合法报告。容器不接收作者配置的 `NOCTF_CHECK_REQUIREMENTS`。签名回调继续验证枚举、重复项、时间、Flag 归属和执行身份。

Control 配置镜像、有序命令、环境变量、目标服务和超时。Worker 派发任务，目标所属 Runner 执行一次性容器。容器读取 `NOCTF_TARGET_HOST`，使用 `NOCTF_CALLBACK_URL` 和 `NOCTF_CALLBACK_TOKEN` 提交结构化结果。`Controlled` 携带控制标识，`Uncontrolled` 不携带标识，`Indeterminate` 报告稳定故障码。平台按比赛题目和有效期匹配队伍，未知标识记为无人控制，歧义记为平台故障。

回调、正常退出、辅助资源清理和容量释放共同完成观察。重复回调幂等，冲突拒绝；过期、跨 Runtime、已停止目标的回调不能更新结果。模板 Control 测试返回 `202 + statusUrl`，保留交互目标，不产生正式比赛事实。

## 升级顺序

1. 记录现有赛事、题目、队伍、事实与运行环境标识，导出现有 Control 配置供作者参考。
2. 停止受影响的执行，备份 PostgreSQL、认证及加密密钥、Data Protection 密钥和上传文件。停止 JetStream 写入后备份其数据目录。
3. 在独立 PostgreSQL 恢复备份并运行迁移，核对业务标识和数量。
4. 保留 `20261105094930_InitialBaseline`，应用 EF 生成的 `20261106171504_ContainerCapabilityExecution`。不要修改生成的迁移或 snapshot。
5. 更新 Host 与前端。缺少镜像的旧 Control 显示待配置，作者补齐配置前禁止执行、测试、发布和开赛。
6. 核对登录、配置编辑、真实 Check / Control、排行榜及重启后的数据保留，再恢复正常执行。

迁移删除模板验证清单和旧 Control HTTP 字段，保留历史结果及执行记录。迁移不会生成替代镜像或修改已有成绩。升级后的数据库需要与新 Host 配套使用；恢复旧部署时应恢复完整备份。

Docker 测试与预览 Runner 共享同一资源域时，应串行运行，防止独立部署的资源回收器相互干扰。Kubernetes 验收使用独立 kubeconfig、支持 NetworkPolicy 的 CNI、已核验的 PID 配置和可实际拉取的测试镜像，不操作现有集群。
