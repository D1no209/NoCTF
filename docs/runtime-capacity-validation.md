## 负载与恢复

CPU 倍率 1/2 × 16/64 请求共四种真实 Redis/Docker 用例全部通过。每种均包含空闲、
启动突发、持续 CPU 负载；每种发生三次隔离测试 Redis 全丢。在 0.85 CPU 预算中，
主工作负载分别容纳 3 / 6 个 0.2 CPU Limit 的容器，同时保留一个严格 0.25 CPU Checker。
内存和 PID 保持完整 Limit。66 次真实创建及停止完成，重复释放后余额精确回到配置额度。

原始数据在 [validation/runtime-capacity-20260918](validation/runtime-capacity-20260918/summary.csv)。
`createMs`/`stopMs` 是真实 Provider 生命周期调用；`claimBatchMs` 为一批并发领取，
`queueMs` 仅包含成功准入的请求（未准入数单列）；`recoveryMs` 是 Redis 重建供给的
已提交分配文档。此组件实验的 PostgreSQL 调用为 0，数据库提交/恢复语义由独立集成测试验证，
不能把这些恢复延迟当作完整 Runner 启动延迟。Redis 命令计数包含诊断/观测注册和清理。

该负载测试使用健康观测夹具。另在同机 Docker VM 实际 `/proc`、cgroup 和 Docker API 上
执行宿主压力实验：32 CPU、约 31.15 GiB；.NET 10.0.10 / Ubuntu 24.04。默认 90%/20 秒
压力阈值触发阻断，停止负载后三个健康样本恢复；测试耗时 59 秒。采集原始数据见
[docker-host-pressure.json](validation/runtime-capacity-20260918/docker-host-pressure.json)。
初次有效采集包含建立数据库所有权连接，不等价于稳态采集开销。

每项两次进程启动、12 次预热、12 次采样、每次 512 次调用，依次执行，期间不运行其他测试。
