# 平台日志查询、实时查看与导出

入口：平台设置 → 日志，`/admin/platform/logs`。管理员读取私有 Loki 中的脱敏技术日志。Docker 基础部署默认关闭观测，需要按 [监控安装](../../operations/monitoring.md)准备。

## 筛选字段

选择最低级别、服务来源、起止时间和搜索文本，再应用筛选。最低级别包含更严重日志；服务来源区分 Api/Worker/Runner 等，避免只查 Api 漏掉异步评测执行。

时间按本地输入转 UTC，跨角色调查使用同一窗口，最好保留 Runtime/GameplayFact 等关联 ID。当前界面为有界 cursor 页码：每页 20/50/100/200 条，上一页/下一页沿服务器签名游标读取，不提供任意 offset 跳转或精确历史总页数。

## 操作流程

1. 选定问题发生窗口和来源，应用筛选。
2. 从当前第一页读取，使用上一页/下一页和每页数量查看历史。
3. 查看稳定 failure code 与关联 ID，跳转对应业务事实核对。
4. 开启/关闭实时读取观察新匹配记录。
5. 需要离线材料时设置明确起止时间并导出 JSONL。

应用筛选会固定本次查询条件与时间窗口；未填时间时默认使用当前结束时刻前 14 天。切换每页数量回第一页。

实时新到达只增加新日志提示，不插入正在阅读的历史页、不挤掉未读行。点击“查看最新”重新取得第一页；未固定终点时会更新窗口。游标过期/失效则按页面反馈重新查询，不手改 opaque cursor。

## 导出

导出得到 `platform-logs.jsonl`，一行一条记录，按所选最低级别、来源、时间和搜索条件读取。验证文件可读、窗口和范围正确，保存到受限调查目录。

同步流式下载中断后确认是否完整，不能根据“开始下载”提示认定导出全部完成。

## 脱敏与解密

日志导出前脱敏，不保存原始 Flag/JWT/SQL 参数或明文 UserId。受保护内部 UserId 需要 reader 使用与各角色一致的 RunnerScoring key 解密；轮换前规划所需审计窗口。

不可读 protected document 应返回故障，不伪造“零日志”。Loki 未配置、断连、筛选窗口错误和真实没有记录需要分开判断。

## 日志与审计

### 查看安全诊断信息

带异常的日志可包含异常类型链、NoCTF 方法名及行号、操作来源，以及数据库 SQLSTATE 和经过校验的表/列/约束名称。Warning 及以上记录可提供 trace ID。排障时结合时间、服务来源、操作来源和 trace ID，定位同步请求或异步处理阶段。

原始异常消息、SQL、参数以及 PostgreSQL Detail/Hint 等敏感内容继续受到限制。字段未显示时先查看当前记录类型及可用诊断内容，避免通过扩大日志输出暴露凭据或 Flag。

### 区分重试与持续失败

可重试的数据库事务冲突（SQLSTATE `40001`、`40P01`）对应的 EF 事件记录为 Information，业务层执行有界重试。重试耗尽仍会通过调用方报告失败，其他数据库错误继续按原级别处理。调查事务争用时可临时将最低级别设为 Information，并核对最终业务状态。

角色首次健康前的两分钟内，readiness 尚未就绪记录为启动进度（Information，事件 4103）；超过此窗口，或角色曾经健康后再次失败，仍按故障处理（事件 4100）。启动进度日志不改变 readiness 响应，实际上线仍要求健康检查通过。

日志说明技术失败，权威业务状态来自当前事实。想查“谁做了什么”使用 [审计](./audit.md)，想查网络证据使用 [抓包](../../competition/operations/traffic-captures.md)，它们不能互相替代。
