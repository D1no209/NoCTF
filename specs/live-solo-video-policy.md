# LiveSolo 视频资源策略

平台管理员在「平台管理 → 实验功能 → LiveSolo 视频资源」调整当前部署的视频策略。
比赛和选手不能覆盖该策略；原有四种赛制不加载媒体 SDK，也不使用这些限制。

| 参数 | 默认 | 允许范围 |
|---|---:|---:|
| 最大宽度 | 1280 px | 320–3840 px，偶数 |
| 最大高度 | 720 px | 180–2160 px，偶数 |
| 最高帧率 | 10 FPS | 1–30 FPS |
| 每路屏幕最高码率 | 1000 Kbit/s | 128–8000 Kbit/s |

数据库和 API 使用 bit/s，界面使用十进制 Kbit/s（1 Kbit/s = 1000 bit/s）。
宽高是边界，采集保持来源比例；较小来源不放大。浏览器发布使用 H264，关闭
simulcast、backup codec 和额外编码层。首次共享、重新共享、重连及替换采集轨道
都应用限制；不支持这些约束的浏览器停止共享并提示错误。

选手媒体接口只返回有效宽高、帧率、码率和策略标识。每次读取都查询权威数据库；
请求不能指定导出预算。选手界面另显示实际发送统计，未知数值显示为未验证。
编码目标码率不是网络流量的硬上限；RTP 重传和协议开销仍需纳入容量测量。
SFU 对自定义恶意发布器的硬码率／尺寸限制尚未验收，不能把浏览器约束当作该保证。

## 修改后的生效时间

- 已连接的 NoCTF 浏览器在下一次媒体状态刷新后调整当前采集轨道和编码器，
  不重启 Match，也不因配置修改重新连接媒体房间。
- Programme 合成仍需转码，整路输出使用同等码率预算，而非按屏幕数相乘。
  活动任务保留启动时参数；下一分段或新任务使用最新策略。
- 单轨录像使用 Egress PASSTHROUGH，不增加一层解码／编码。H264 来源归档为 MP4，
  来源本身变化会反映到录像；启动快照不能被解释为之后所有帧的质量保证。
- Programme／录像各自持久保存启动策略标识、宽高、帧率和码率。
  旧任务无快照时保持未知，不推断旧参数。
- 录像容量仍按实际配置的导出字节上限预留三份副本。降低默认视频码率不会缩减
  活动任务预留；原始副本清理成功后才释放对应预算。

仅 StaffOnly 的比赛会明确提示屏幕与延迟节目不对外公开。采集仅由选手主动点击触发，
连接房间不会申请屏幕、摄像头或麦克风权限；录像开关与临时节目片段用途分别说明。

浏览器使用 SDK 明确提供的发布／订阅分离连接配置
（[RoomOptions.singlePeerConnection](https://docs.livekit.io/reference/client-sdk-js/interfaces/RoomOptions.html#singlePeerConnection) = false）。
本地浏览器默认单连接握手在 `RTCPeerConnection.setConfiguration` 失败；显式配置后
同一真实房间连接成功。它只选择传输方式，不增加视频编码层，也不增加自动重试适配器。

## 验证记录

EF 工具生成增量迁移，旧平台设置得到上述默认值；OpenAPI 和 SDK 已重新生成。
PostgreSQL 测试覆盖策略持久化、事务回滚、独立修订、其他设置保留，以及启动参数和
三份预留在策略降低后保持。前端覆盖比例适配、约束失败、单层编码、重新共享、
重连、替换轨道及不停房间的策略更新。实际管理员界面验证了修改、保存、重载和还原。

同一合成负载的性能观测见 [本地媒体负载记录](live-solo-load-validation.md)。
这些观测不替代真人窗口选择、50 个视频解码浏览器、跨节点恢复或生产媒体部署验收。
