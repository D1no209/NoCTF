# Checker 如何读取 Fix 输入和修补产物

先在前端进入“题库管理 → 该题目 → 模式定义”，打开“启用 Fix 一次性验证 Checker”和“向 Checker 提供 Fix 包”，
然后点击“保存修改”。平台只提供选手上传包的规范化副本，不能把它当成修补后的靶机快照。

| 需要检查的内容 | 读取位置／做法 | 平台是否自动提供 |
| --- | --- | --- |
| 选手随包上传的替换源码、二进制、配置 | `/noctf/fix/<包内相对路径>` | 打开“向 Checker 提供 Fix 包”后提供 |
| `fix.sh` 执行后生成的文件 | 在 Checker 自己的同版本基线上受控重放后，读取重放工作目录 | 不自动生成，需出题人实现 |
| 真实防御靶机当前的磁盘文件 | 当前契约没有自动复制／挂载／下载接口；通过公开业务行为验证，或另行评审需求 | 不提供 |

三个来源不能互相冒充。重放产物可能因环境、随机数、时间或外部依赖与真实靶机不同，最终仍应访问
`TARGET_HOST` 验证真实服务；不要向靶机新增回调凭证读取口或把 Checker 的敏感文件传回去。

## 方案一：读取选手输入文件

假设选手归档包含 `fix.sh` 与 `policy.txt`，打开上述前端开关后，平台在 Checker
启动前准备好 `/noctf/fix/fix.sh` 和 `/noctf/fix/policy.txt`，无须自行下载、再次解压或寻找原始 tar 路径。

示例工具 [inspect-file.py](checker/inspect-file.py) 只读取固定目录中的普通文件，并输出来源、相对路径、
字节数和 SHA-256，不执行脚本或二进制，不打印原始内容：

```sh
python3 /checker/inspect-file.py --source input --path policy.txt
```

工具默认最多读取 16 MiB，超限、文件缺失、目录、路径越界或符号链接会明确报错并非零退出。
这只是文件结构与来源检查，退出 0 不代表防御成功；出题人仍需实现内容、功能与漏洞判定。
如要检查上传的替换二进制，可将路径改为本题约定的 `bin/service`，并根据题目资源预算审核大小上限。

## 方案二：检查执行修补后生成的文件

Checker 必须自己携带与靶机一致的原始基线，并让重放过程在明确的隔离边界内运行：

1. 将 `/opt/noctf-baseline` 复制到 `/tmp/noctf-fix-work`，另存修补前副本。
2. 把选手输入注入重放隔离环境，使用约定的相对输入路径执行 Patch。
3. 限制重放进程的时间、进程数、网络和可访问文件；不能让它读取 Checker 的回调令牌、原始基线或判定脚本。
4. 检查工作目录中的生成文件，再比较修补前后的差异。
5. 独立执行正常业务与漏洞探测，不把重放成功当作整个防御成功。

本教学模板的 [replay-and-diff.sh](checker/replay-and-diff.sh) 演示基线复制、
`NOCTF_TARGET_ROOT` 约定、差异输出和服务自检；关键词扫描和脚本里的“扩展点”不是已经实现的安全沙箱。
**该直接重放示例仅可用于可信的教学样例，不可直接执行真实选手的不可信脚本。**

完成可信教学重放后，可检查工作副本：

```sh
# 先由你的隔离重放流程准备好 /tmp/noctf-fix-work。
python3 /checker/inspect-file.py --source replay --path policy.txt
```

这里读取的是 Checker 的 `policy.txt`，不是防御靶机上的文件。若 Fix 是现场编译生成程序，需在重放环境
提供同版本编译工具，并核对产物与运行行为；不能直接检查 `/noctf/fix` 就声称已读取现场编译产物。

## 发给出题 Agent 的约束

```text
为 NoCTF AWDP 编写 Checker 时，先在部署说明登记需要的文件来源：input、replay 或真实靶机。
input 仅指前端打开“向 Checker 提供 Fix 包”后的 /noctf/fix，包含选手包副本，不是靶机快照。
若需要生成后的附件，必须说明在独立基线中如何隔离重放，以及环境一致性如何验证。
不要默认把选手脚本直接放到持有 NOCTF_CALLBACK_TOKEN 的 Checker 进程环境执行。
读取文件时检查相对路径、普通文件类型、链接与大小；不执行上传二进制来“验证文件存在”。
不要假定 Checker 自动获得 FLAG，不要以依赖缺失、写目录失败或连接超时代表 EXP 已被修复。
必须验证真实 TARGET_HOST 的正常业务，再进行漏洞探测，最后按既有回调协议报告结果。
若要求真实靶机执行后的磁盘文件，明确标记当前接口不提供，不能编造共享目录或下载 API。
```

`ServiceAbnormal`、`ExploitSucceeded`、`DefenseSucceeded` 是业务判定；依赖或回调等基础设施故障
应保留非零退出。具体环境变量和超时见 [字段字典](../platform/FIELDS.md)。
