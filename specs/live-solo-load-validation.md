# LiveSolo 本地合成媒体负载记录

日期：2026-10-10。成功复测基线：`f597ade7`；独立本地测试环境，没有访问生产服务。
下文初次结果之后，又在 `66d85215` 基线上重建隔离数据库及消息服务，完成暂存挂载／三份预算／独立媒体队列复测。

## 测试范围

实际 Production Api + Worker、PostgreSQL、Redis、NATS JetStream、固定版本 LiveKit SFU 和 Egress。
四个独立 Match，各有两队、每队两名经过真实登录和锁定名单的测试用户。
16 个 Node 发布器生成 640×360、约 15 FPS 的 H264 SCREEN_SHARE；Egress 输出默认 1280×720。
50 个独立 HTTP 观众通过正式浏览器绑定租约接口进入、续租，读取元数据、播放列表及新视频片段。
这不是真人桌面采集或 50 个解码浏览器；另有一个真实浏览器成功解码节目和已归档 MP4。

Docker Desktop 提供约 31 GiB 内存，本机 32 个逻辑处理器；测试期间用户其他开发容器仍运行。
资源采样仅选择本次所属容器；媒体池使用一个未限制 CPU 的 Egress 实例。
Windows 宿主及 Docker Desktop 的结果不能直接推算生产 Linux 容量。

## 失败结果与修复

- 初次观众负载存在续租 409，修复为独立租约行并发控制后复测成功。
- 初次私有通知 P95 913 ms，媒体导出和私有失效通知分离队列后测得 63 ms。
- 初次开启录像有两项启动超时，保持未知状态及预留，没有自动重新启动或绕过倒计时。
- 下一次发现两条从未发出启动请求的失败记录；源在启动前失效。新增强类型原因和经理复核重试，
  要求恢复同一轨道；不同轨道不能重试原请求。后续新场次确认全部 16 路录像后才开始。

## 存储与剩余验收

成功负载基线尚未挂载 Egress 的内部暂存目录。现场发现 `/home/egress/tmp` 约 1.1 GiB，
而 `/out` 采样最高仅约 1.49 MB；此前 spool 数字不能代表全部原始视频占用。
托管存储采样包含先前测试归档和并行清理，同样不能视为本轮净增长。
后续实现将暂存目录放入专用固定容量挂载，读取活动文件大小并计入三份副本预留；
该改动后的完整负载仍须重新验证。

### 暂存与独立队列复测

新场次的四场 Match 均通过真实录像／节目就绪检查，16 路录制保持活动。
50 个 HTTP 观众持续 92.18 秒：6,527 次请求、882,771,597 字节、零错误，
HTTP P50 41.03 ms／P95 117.61 ms；第 51 个观众返回 429，未观察到提前状态。
同时 16 个私有 Hub 客户端收取 32 次对局通知：P50 35 ms／P95 43 ms／最大 44 ms。

10 次所属容器采样中，Egress 峰值 CPU 1,172.34%／内存 9.51 GiB，SFU 峰值 23.40%／155 MiB；
Host 平均 1.04 核、峰值 534.22 MiB。spool（已包含内部暂存）采样峰值 1,356,469,571 字节；
它包含此前实验留下的文件，不能当成本轮净增长或每场需求。

负载完成后，四场分别通过实际 Flag 提交受理并完成 1:0；16 份 MP4 全部归档，合计 686,043,034 字节。
初次核查有两份清理标记因事务冲突尚未完成，关系化扫描重新派发后数据库确认全部 16 份原始副本清理完成。
这是本地持久目录绑定；固定容量的生产文件系统、满盘行为和人类视频容量仍未验收。

生产默认单实例 4 CPU / 4 GiB 不能承诺四场、16 路录像；本次录制峰值已超过它。
必须在实际部署资源、视频分辨率和码率下重新测量并扩容；不能通过降低提供方资源估值强行准入。
还缺真人屏幕选择、50 个解码观众、原始裁判视频 ≤2 秒、跨节点故障恢复、
固定持久文件系统和 TLS 部署验收。完整 LiveSolo 发布条件尚未满足。

原始日志、含短期测试凭据的数据和截图保留于忽略的 `backend/artifacts/live-solo-real-host/`，不提交凭据。

## 720p／10 FPS／1 Mbit/s 平台策略与透传复测

平台策略默认 1280×720、10 FPS、每屏 1,000,000 bit/s；Programme 合成输出也使用
10 FPS／1000 Kbit/s。录制改为单轨 PASSTHROUGH，不再把 640×360 来源转码并放大。
管理员浏览器验证修改为 8 FPS、保存、重载恢复，再还原 10 FPS后进行正式测量。

两组四场均通过正确 Flag 提交完成 1:0；最初结束脚本错误使用 on/off 作为合成题标识，
这些提交正常判 Wrong，改用实际合成题标识后才完成。开启组 16 份 MP4 全部归档，
合计 83,681,546 字节。工作人员浏览器成功解码一份 145.919 秒的录像：
640×360、readyState 4、无媒体错误。没有放大到 Programme 的 1280×720。
原始副本经关系化重派发最终确认 16/16 清理完成。

本次降低帧率、节目码率和去掉录制转码同时生效，结果不能单独归因于某一项。
与此前 15 FPS 输入／15 FPS、1800 Kbit/s 节目基线相比，开启录制的 CPU 和内存降低，
但单实例仍超过 4 GiB，不能承诺默认 4 CPU / 4 GiB 的部署承载这组负载。
录像时长与既有基线不一致，文件合计大小不能直接当作相同时间的节省比例。

合成内容是移动色块，本次没有验证真实代码文本可读性。真人专用窗口的授权选择、
采集实际限制、原始裁判延迟、50 个解码观众、多节点、固定容量文件系统及生产部署
仍是独立未完成的验收项。SFU 对自定义发布器的硬流量限制也未验收。
