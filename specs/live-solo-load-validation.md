# LiveSolo 本地合成媒体负载记录

日期：2026-10-10。成功复测基线：`f597ade7`；独立本地测试环境，没有访问生产服务。

## 测试范围

实际 Production Api + Worker、PostgreSQL、Redis、NATS JetStream、固定版本 LiveKit SFU 和 Egress。
四个独立 Match，各有两队、每队两名经过真实登录和锁定名单的测试用户。
16 个 Node 发布器生成 640×360、约 15 FPS 的 H264 SCREEN_SHARE；Egress 输出默认 1280×720。
50 个独立 HTTP 观众通过正式浏览器绑定租约接口进入、续租，读取元数据、播放列表及新视频片段。
这不是真人桌面采集或 50 个解码浏览器；另有一个真实浏览器成功解码节目和已归档 MP4。

Docker Desktop 提供约 31 GiB 内存，本机 32 个逻辑处理器；测试期间用户其他开发容器仍运行。
资源采样仅选择本次所属容器；媒体池使用一个未限制 CPU 的 Egress 实例。
Windows 宿主及 Docker Desktop 的结果不能直接推算生产 Linux 容量。

资源峰值分别来自 6、13 次采样，可能漏掉短暂峰值。网络计数为长期测试容器的累计值，
不能当作本轮带宽；上表读取字节是本轮 HTTP 响应的准确计数。

开启录像时同时连接 16 个真实 WebSocket/SignalR 客户端，执行四场 Pause/Resume，
收到 32 次对应 Match 失效通知：P50 33 ms、P95 63 ms、最大 63 ms，无错误。
这是提交时间到通知到达的本机测量；尚无跨节点或原始裁判视频延迟结论。

第一场随后通过实际 Flag 受理序号 1 完成 1:0。四份录像归档为 40,864,350、
41,174,175、41,001,788、41,935,151 字节；工作人员浏览器读取受限预览流，
解码到 1280×720、readyState 4（选中录像约 199.8 秒）。观众浏览器播放旧片段时仍显示旧 0:0，
独立延迟结算显示 1:0；没有把最终成绩覆盖到旧视频帧。

## 失败结果与修复

- 初次观众负载存在续租 409，修复为独立租约行并发控制后复测成功。
- 初次私有通知 P95 913 ms，媒体导出和私有失效通知分离队列后测得 63 ms。
- 初次开启录像有两项启动超时，保持未知状态及预留，没有自动重新启动或绕过倒计时。
- 下一次发现两条从未发出启动请求的失败记录；源在启动前失效。新增强类型原因和经理复核重试，
  要求恢复同一轨道；不同轨道不能重试原请求。后续新场次确认全部 16 路录像后才开始。

## 存储与剩余验收

成功负载基线尚未挂载 Egress 的内部暂存目录。现场发现 `/home/egress/tmp` 约 1.1 GiB，
而 `/out` 采样最高仅约 1.49 MB；此前 spool 数字不能代表全部原始视频占用。
托管存储采样包含先前测试归档和并行清理，同样不能视为本轮净增长。
后续实现将暂存目录放入专用固定容量挂载，读取活动文件大小并计入三份副本预留；
该改动后的完整负载仍须重新验证。

生产默认单实例 4 CPU / 4 GiB 不能承诺四场、16 路录像；本次录制峰值已超过它。
必须在实际部署资源、视频分辨率和码率下重新测量并扩容；不能通过降低提供方资源估值强行准入。
还缺真人屏幕选择、50 个解码观众、原始裁判视频 ≤2 秒、跨节点故障恢复、
固定持久文件系统和 TLS 部署验收。完整 LiveSolo 发布条件尚未满足。
