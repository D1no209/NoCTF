## 2. 题面与预期攻击面

### 2.1 题目目标

待填写：选手需要审计、利用和加固的功能。

### 2.2 预期漏洞

待填写：漏洞位置、触发条件、预期利用链，以及为什么能读取当前动态 Flag。

### 2.3 合法加固边界

待填写：允许修改的范围、必须保留的业务功能、明确禁止的绕过方式。

待填写：Checker 用于判断服务可用性的请求、预期状态码和关键响应条件。

## 3. 题库模板配置

### 3.1 Runtime

- [ ] 分配方式为 `PerTeam`。
- [ ] Flag 来源为 `AwdRotation`。
- [ ] Runtime 为 Container 或 Compose，没有 OVA。
- [ ] 服务监听 `0.0.0.0` 上的固定容器端口。
- [ ] 对外端口的宿主端口保持 `0`，不写死宿主端口。
- [ ] 攻防入口使用 `Participants`；只供本队的管理入口使用 `OwnerOnly`。
- [ ] 内存、CPU、PID 上限已按压力测试设置。
- [ ] 镜像不依赖宿主路径、Docker Socket、特权模式或平台内部网络。
- [ ] 安全选项与镜像 `USER`、写入目录相容。

Runtime 配置摘要：

| 项目 | 内容 |
| --- | --- |
| 启动命令 argv | 待填写；使用镜像默认入口时注明“默认” |
| 环境变量 | 待填写；不得包含真实 Flag 或秘密 |
| 对外端口 | 待填写：容器端口、协议、URL 模板、Exposure |
| 内部端口 | 待填写 |
| TTL | 待填写或“不设置” |
| 操作超时 | 待填写 |
| no-new-privileges | 开启 / 关闭，原因：待填写 |
| 只读根文件系统 | 开启 / 关闭，原因：待填写 |
| 非 root | 开启 / 关闭，镜像 USER：待填写 |
| CapDrop / CapAdd | 待填写 |

保存 Runtime 定义后，应在题库“运行环境”页启动测试容器，确认镜像、动态端口、入口显示和测试 Flag
注入均正常；停止测试容器只回收实例资源，不主动删除 Runner 镜像缓存。

### 3.2 动态 Flag 注入

> 这里只描述“如何注入”。Flag 前缀和正文模板在比赛题目规则中配置。

| 项目 | 内容 |
| --- | --- |
| 注入目标 | 文件 / 进程 / 服务内部接口：待填写 |
| 注入命令 | 待填写，必须包含精确的 `${FLAG}` |
| Compose ServiceName | Container 填“不适用”；Compose 填待填写 |
| 超时 | 待填写秒，建议 3～10 秒 |
| 原子更新方式 | 待填写 |
| 重复执行幂等证明 | 待填写 |
| 服务读取最新 Flag 的方式 | 待填写；禁止只在首次启动时读取 |

注入命令示例（交付时替换为本题真实命令）：

```sh
printf '%s' '${FLAG}' > /dev/shm/flag
```

### 3.3 Checker

| 项目 | 内容 |
| --- | --- |
| Checker 镜像 | 待填写 |
| 启动命令 argv | 待填写或“镜像默认入口” |
| 目标服务 | Container 填 `target`；Compose 填服务名 |
| 目标端口 | 待填写 |
| 单次超时 | 待填写秒 |
| Up 条件 | 待填写 |
| Down 条件 | 待填写 |
| 预计最大执行时间 | 待填写 |

Checker 必须完成：

- [ ] 使用 `NOCTF_TARGET_HOST` 访问隔离网络中的目标。
- [ ] 向 `NOCTF_CALLBACK_URL` 提交严格的 `Up` 或 `Down`。
- [ ] 使用 `Authorization: Bearer $NOCTF_CALLBACK_TOKEN`。
- [ ] 回调成功后以 0 退出。
- [ ] 不输出 Token、Flag、完整敏感响应或凭据。
- [ ] 对连接失败、HTTP 错误、超时和异常响应有确定行为。
